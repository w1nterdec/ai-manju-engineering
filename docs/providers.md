# 模型接入与能力协商

## 当前状态

`manju/providers.py` 仅定义 `Capabilities`、`GenerationRequest`、`GenerationResult` 和 `Provider` 协议，没有真实模型适配器。当前 CLI 不调用云服务，不接受 API 密钥，也不会产生合成费用。

先跑通一个镜头，再选择真实供应商。工具品牌只是候选，选择依据是可验证能力、质量、成本、地区可用性、授权与可维护性，不依据宣传中的“最好”。

## 每类接口必须回答的问题

**文本/编剧**：能否保持结构化契约？上下文与输出上限是多少？是否能保持事实来源、引用原句并标出缺失信息？模型输出必须重新进入静态校验，不得因“JSON 模式”跳过语义引用检查。

**TTS**：实际音色是否支持姓名读音控制？控制格式是什么？多音字能否按词区分？是否有字级时间戳？人物音色是否能跨请求固定？数字、方言、轻声和情绪怎样处理？

**图像**：是否支持角色参考图、局部编辑、姿态控制、多个角色分别绑定及需要的画幅？一张图的成功不代表双人镜头也成功。记录实际参考图及模型版本。

**视频**：是否支持批准的首帧/尾帧、所需时长、分辨率、镜头控制和任务查询？原生声音能否精确控制姓名？不支持时应回到单独配音与后期工作流。

**后期**：能否探测真实时长、帧率、音量、字幕对齐与口型？FFmpeg 等确定性工具适合组装、探测与转码；自动剪辑不能代替叙事审核。首版没有调用 FFmpeg。

## 接入规范

1. 以确切模型、音色、接口版本登记能力，调用 `capabilities.require(kind, controls)`。关键控制项不支持则显式失败，不能丢弃。
2. 将编辑层读音、参考图和动作意图转换为供应商格式，并记录实际请求。只把接口接受的字段发过去，不把整份制作说明机械塞进提示词。
3. 请求记录须包含模型、参数、输入媒体摘要、模板版本、任务 ID、幂等键和预算。seed 仅在支持时登记。
4. 结果记录须包含供应商任务 ID、实际模型和参数、实际输出文件、带币种的金额；未知金额用 null 表达，不得以 0 冒充未知，不同币种不得直接相加。
5. 对限流和临时失败设置有上限的重试。超时先查询原任务，避免重复生成和重复扣费。明确可取消行为与失败原因。
6. 测试分为无网络契约测试和人工触发的真实集成测试。供应商能力变化时保留兼容记录，不自动把新版本当成已验收版本。

## 首轮建议验证的路线

- 先接一个有明确读音控制的 TTS 接口，解决最容易听到且可按句返工的问题。
- 再接一个有角色参考与编辑能力的图像接口，验证单人、双人、道具和局部修补。
- 然后接一个图生视频接口，验证动作完整性与时序漂移。
- ComfyUI 可以作为受控图像/视频工作流候选，其官方路由文档提供队列与历史查询机制；真正接入时仍需固定工作流、模型文件与自定义节点版本。

这些是验证顺序，不是已经接通的供应商清单。[官方证据与范围](references.md) 单独维护，避免把能力介绍当成评测结论。
