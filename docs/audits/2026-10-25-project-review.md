# 项目审查：0.8.2 的实际能力与下一步

审查日期：2026-10-25（Asia/Singapore）。基线：main `d25bbd623b66045edec87d2c5a1b60b63740fbf9`，版本 0.8.2。本轮是审查与路线规划，没有修复下列运行时问题，也没有调用生成服务、使用真实密钥或导入客户素材。

## 判断

项目已具备可复现的离线流程、明确的编辑契约和较完整的记录机制；真实媒体链路、模型效果、实际账单和客户交付仍未验证。建议定位为“中文漫剧的制作与质量控制层”，先证明姓名读音、角色/道具连续性和剧情事实在真实作品中正确，再扩大模型与业务覆盖。

96 项测试通过证明已覆盖场景未回归，不等于生产边界无缺陷；本轮在既有测试之外复现四项 P2。未测代码覆盖率、吞吐、实际姓名正确率或商业转化，因此不提供成熟度百分比或行业排名。

## P2：四项可复现缺陷

### A1：拷贝中断留下坏的内容寻址对象，重试无法恢复

位置：[assets.py:18–26](../../manju/assets.py#L18)。先计算源摘要，再直接向最终 blob 路径写入。中途异常会保留不完整文件；再次导入同一源文件时因摘要不符被拒绝。

复现：用合成文本作为素材，注入 copyfileobj 写入四字节后中断。最终 blob 存在但不匹配文件名摘要，正常重试抛出 ValueError。

影响：素材导入/恢复路径；没有证据表明坏对象会被静默当成有效素材。

建议：同卷临时对象中流式拷贝并计算实际内容摘要，完整关闭/fsync 后再发布；错误时不留下最终路径。对已存在坏对象应明确隔离与恢复，不覆盖有效对象。验收包括中断后可重试、源文件拷贝期间变化和既有正确对象不被破坏。

### A2：自定义画像模板可覆盖核心项目配置

位置：[business.py:49–61](../../manju/business.py#L49)。模板名只检查是目录内 JSON 文件，没有排除 production.json、profile.json、project.json、delivery-checklist.json 等保留名。

复现：在合法画像 templates 中增加 production.json，内容为合成标记。new_project 创建的正式配置被覆盖，随后 load_config 无法读取。

影响：自定义画像可被校验接受，却生成不可用项目。这不是已证明的远程执行漏洞。

建议：在创建输出目录前拒绝保留文件名冲突，同时验证模板值与敏感字段策略；四种内置画像和非保留自定义表单保持可用。

### A3：额外素材变更未进入任务输入和失效链

位置：[planning.py:27–44](../../manju/planning.py#L27)、[assets.py:141](../../manju/assets.py#L141)、[business.py:149](../../manju/business.py#L149)。身份绑定的素材进入 identity 任务；additional_assets 虽出现在配置/记录中，没有绑定到具体图像任务参数或依赖。

复现：对同一构建使用两份不同的、技术批准的合成商品参考资产。plan_id 改变，但全部任务 key 不变；执行完成后 sync 新计划，没有任何任务 stale。

影响：当前可观察到 mock 缓存未失效、参考资料没有传到生成请求；不能据此声称已经观察到真实错误画面。真实图像接入后会直接影响商品、场景、道具和风格替换的正确性。

建议：建立逐任务 asset_ids/角色与用途映射，把批准版本及内容摘要同时写入请求和任务 key；只重建实际依赖该素材的任务。不要通过把整个配置摘要塞进所有任务来放弃局部重建。

### A4：演示打包只重算外层摘要，未核对运行产物与血缘

位置：[delivery.py:169–178](../../manju/delivery.py#L169)、[assets.py:154](../../manju/assets.py#L154)。lineage 核对计划与构建关联，但没有逐项核对运行产物；复制 trace 文件时也没有比对 status 中记录的 sha256/media_sha256。

复现：完成 mock 运行后改写 image:S001 的产物，再直接执行 demo package。打包成功，verify-package 外层完整性通过，但包内文件与 lineage.json 中的原摘要不同。

影响：本轮证明的是 mock 演示包内部来源不一致。生产模式的审核媒体另有摘要检查，且当前 mock 运行被生产模式拒绝；未证明实际生产门禁可被绕过。

建议：打包前集中核对所有声明的运行产物，复制后再次核对；独立校验可选增加来源索引一致性检查。说明“包内文件完整”与“确为已审核来源”是不同保证。

这是历史审查观察脚本，不加入普通 CI 作为“缺陷必须存在”的测试。修复时应将四个场景转为断言恢复、拒绝或正确失效的回归测试。本轮没有修复这些缺陷。

## 架构与产品层面的缺口

已有的价值：原剧本为台词单一来源、稳定 ID、状态链、构建快照、预算预留、追加事件和显式 mock 标记。这些值得保留，不需要重写成微服务。

主要缺口：

- 实媒证据：PCM 时长有真实字节测量；视频技术、实际中文纠音、身份保持与语义忠实度仍没有真实端到端证据。生产正向记录测试包含注入结果，不能视为成片验证。
- 接入边界：不能直接将 MockProvider 替换成 HTTP。注册表、CLI、执行器、mock 判定、契约套件和账本均需分层处理；当前 plan.mock 按 offline 推导，账本结算写 mock=true，真实费用的不确定状态尚未建模。
- 易用性：真实生产需要人工组织多份 JSON、摘要、授权与来源记录；缺少媒体导入与安全的表单生成入口。优先减少这一步的手工拼装成本，再讨论复杂工作台。
- 分发：安装后的模板/示例/配置资源发现、非仓库目录运行与升级迁移缺少验证。源码能运行不能替代可安装产品。
- 质量证据：没有真实姓名出现次数、剧情事实传达、角色一致性、返工和单位合格时长的原始分母与失败样本。缺少这些，无法判断提示词工程改善了多少。
- 焦点：四画像和八能力接口提供了扩展边界，尚未证明四种业务都可交付。下一阶段集中连续漫剧，保留其余画像而暂缓扩展。

## 定位与成长建议

建议的差异化是“可追溯的中文读音、剧情与连续性控制”，而非再做通用模型聚合平台。这个方向仍是待验证的产品假设，不是市场独占结论。

官方资料显示，SSML/词典、参考图、队列历史等能力已有可用机制。项目应利用这些能力组织可靠流程，而不是承诺仅靠长提示词消除错误。详见[分阶段成长路线](../growth/2026-10-25-roadmap.md)。

本轮仅检查官方文档，不采购、比较实时价格或调用服务。外部来源如下，as_of 均为 2026-10-25：

- [Microsoft 发音控制](https://learn.microsoft.com/en-us/azure/ai-services/speech-service/speech-synthesis-markup-pronunciation)：有音素与词典机制；需继续核对具体语言、音色和接口的支持范围。
- [阿里云实时 TTS](https://help.aliyun.com/zh/model-studio/realtime-tts-user-guide)：有纠音及精细控制说明；实际模型/音色/接口支持并不相同，不能把文档入口当成已接入。
- [ComfyUI 官方队列与历史路由](https://docs.comfy.org/development/comfyui-server/comms_routes)：已有工作流提交与任务状态机制；此处只确认路线存在，不保证任何特定工作流适用。
